# mdfeed-handler

C++20 UDP market-data feed handler. Receives simulated price updates from
two synthetic venues, normalizes the wire formats into a unified internal
`MdMessage`, maintains a per-symbol BBO (best-bid / best-offer) book in a
flat hash map, and tracks per-message latency with sub-microsecond
granularity via an HDR-style log-linear histogram.

## What this studies

- UDP wire ingest on the standard POSIX `recvfrom` path.
- Multi-venue normalization: a 27-byte little-endian binary format and a
  pipe-delimited ASCII format both decode into the same `MdMessage`.
- BBO state machine: better-side replaces top, same-price refreshes
  qty, cancel at top erodes the side (the depth-fallback case is logged
  and surfaced to the caller).
- Latency measurement methodology: `CLOCK_MONOTONIC_RAW` per-message,
  HDR histogram with 3 significant figures over `[1ns, 1s]`, two
  separate percentile streams (`wire_to_normalized_ns` and
  `venue_to_recv_ns`).

## Differentiation

This is intentionally a different problem from the two adjacent repos:

- `SAY-5/orderbook-sim`, full depth-by-price book + price-time
  priority matching engine. **Write-side** (order entry, matching). This
  repo is **read-side** (wire-to-state, top-of-book only).
- `SAY-5/inference-router`, TCP request/response router. This repo is
  UDP unidirectional broadcast.

## Architecture

```
   feed simulator → loopback UDP (127.0.0.1:42424) → FeedHandler →
       parse → BboBook + HDR latency histograms
```

See [`ARCHITECTURE.md`](ARCHITECTURE.md) and
[`docs/`](docs/).

## Build + run

```sh
make build            # CMake + Release + GoogleTest via FetchContent
make test             # 58 unit + integration tests
make bench            # writes bench/results/bench_local.json
make asan             # rebuild with -fsanitize=address,undefined and rerun tests
make fuzz-smoke       # 5000 iters per parser harness (clang)
```

Or directly:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
cd build && ctest --output-on-failure
./build/loopback_bench --count=200000 --rate=50000 --out=bench/results/bench_local.json
```

Reading the two histograms:

- The **wire-to-normalized** path is sub-microsecond at p99. That's the
  parse + BBO map update + histogram record cost on the consumer side;
  it's a few aligned memcpys plus an `unordered_map` upsert.
- The **venue-to-recv** path is in the **microseconds** range because it
  includes the full `sendto` + loopback + `recvfrom` syscall path on
  the stock POSIX stack. This is the part that kernel-bypass would
  shrink in a real low-latency deployment;
  [`docs/latency-methodology.md`](docs/latency-methodology.md) explains
  why that's deliberately out of scope here.

CI re-runs a 30-second loopback bench at a smaller rate as a smoke
check; numbers there will vary with runner.

## What this is *not*

- Not a real venue gateway. The wire formats are synthetic for the
  study; production wires would be FIX, ITCH, PITCH, or equivalents.
  See [`docs/wire-formats.md`](docs/wire-formats.md) for the swap-in
  path.
- Not multicast. Single unicast UDP, no IGMP group membership. Real
  market data is mostly multicast and adds receive-side filtering
  considerations not covered here.
- Not a full depth book. BBO only. Full depth + matching lives in
  [`SAY-5/orderbook-sim`](https://github.com/SAY-5/orderbook-sim); see
  [`docs/bbo-vs-depth.md`](docs/bbo-vs-depth.md).
- No FIX, ITCH, or PITCH parser. Custom binary + ASCII chosen so the
  study is self-contained.
- No gap fill. Sequence numbers are tracked per venue, gaps are
  counted, but there is no recovery protocol.
- No kernel-bypass (DPDK, ef_vi, Solarflare). POSIX `recvfrom` only;
  the methodology doc explains why and what the swap-in would look like.
- No order entry. Read-side only.
- No CPU pinning, NUMA placement, or hugepage allocation.
